# Auto-Ontology 使用手册（中文）

面向使用这个部署的人：第一次跑起来、日常提问、改本体、接入 Agent、出问题怎么查。
上游英文原文在各 `README.md` / `docs/*.md`，本手册是它们的操作版索引，不重复 API schema。

---

## 1. 它解决什么问题

把"业务语义"做成一层可被 Agent 消费的上下文，让自然语言问数**不只是能查，而是答案可核对**：

| 能力 | 说明 |
|---|---|
| 生成本体 | 从源库元数据自动生成词条（Term）、SQL 属性、关系（Relationship），嵌入存 pgvector |
| 人工认证 | 人在 UI 里改描述、补 SQL 属性、打认证标记；认证过的定义优先被复用 |
| 受控问答 | 问题 → 意图与实体识别 → 语义检索 → 写 SQL → 值校验/SQL 校验 → 执行，返回答案 + SQL + 步骤轨迹 |
| 对外暴露 | MCP（只读工具）、REST（SSE 流式）、CLI/脚本都走同一套权限 |

一句话：**Agent 说得出这个数字是怎么算出来的**，这是它跟"直接 text2sql"的根本区别。

## 2. 系统组成与端口

| 组件 | 技术 | 作用 | 端口 |
|---|---|---|---|
| Frontend | Next.js 16 / React 19 / Better Auth / Prisma | UI、登录、公开 API 网关 | **3000** |
| Backend | FastAPI + LangChain | 问答流水线、目录、本体 API | 3001（内网） |
| Ingestion | FastAPI | 摄入 + 语义编译 | 3002（内网） |
| MCP server | FastMCP | 给 Agent 的只读工具 | 3003（独立进程，不在 compose 里） |
| Postgres + pgvector | PostgreSQL 17 | 目录、本体、应用数据、向量 | 5432 |
| pgAdmin | — | 看库 | 5050（compose） |

> **安全边界**：3001 信任前端转发的 `x-auto-ontology-user-id` 头，不做校验；3002 的 ingest/delete/reset/compile 无鉴权。**这两个端口只能在内网**，对外只暴露 3000。

## 3. 第一次跑起来（Docker Compose）

前置：Docker + Compose v2、`uv`、NVIDIA API Key（`nvapi-...`，来自 build.nvidia.com）。

```bash
cp .env.example .env      # 然后按下面表格填
docker compose up -d --build
```

### 3.1 必填的 `.env` 项

| 变量 | 说明 |
|---|---|
| `DEFAULT_MODELS_API_KEY` | NIM key，问答和摄入都要用 |
| `AUTH_SECRET` | 随机长串（`openssl rand -base64 32`）。缺了所有页面报 Better Auth "default secret" |
| `APP_URL` | 浏览器访问的确切 origin，本地 `http://localhost:3000` |
| `POSTGRES_PASSWORD` | 数据库密码，自己定 |
| `SOURCE_CONNECTION_STRINGS` | **容器内**的源库连接串，host 必须是服务名 `postgres` |
| `AUTO_ONTOLOGY_ADMIN_EMAIL` / `_PASSWORD` | 首个管理员；自助注册是关闭的，这是唯一入口 |
| `PGADMIN_PASSWORD` | pgAdmin 登录密码 |

### 3.2 `localhost` 的坑（必读）

一份 `.env` 同时服务"容器"和"宿主机"两条路径时，`localhost` 的含义不同：

| 变量 | 谁在用 | host 写什么 |
|---|---|---|
| `SOURCE_CONNECTION_STRINGS` | compose 的 `auto-ontology` / `ingestion-service` | `postgres` |
| `CONNECTION_STRINGS` | 宿主机 `uv run`、`dev_tools/` | `127.0.0.1` |

`docker-compose.yml` 里是 `CONNECTION_STRINGS: ${SOURCE_CONNECTION_STRINGS:-${CONNECTION_STRINGS:-}}`：
设了前者用前者，没设则回退到后者（单路径部署不破）。写成 `@localhost` 的容器会去拨自己的回环，报：

```
connection to server at "::1", port 5432 failed: Connection refused
```

### 3.3 模型配置（四个角色 + 回退）

每个角色是一组 `<PREFIX>_ENDPOINT` / `_API_KEY` / `_MODEL`，未设的字段回退到 `DEFAULT_MODELS_*`。

| 前缀 | 作用 |
|---|---|
| `DEFAULT_MODELS` | 共享默认值 |
| `REASONING` | 建本体、写 SQL 与解释、判定可答性 |
| `NON_REASONING` | 意图识别、实体抽取、候选选择、SQL 校验与修复 |
| `EMBED` | 向量化。**摄入与查询必须同一个模型** |
| `RERANK` | 编译期候选表排序 |

两个实测出来的调优项：

- `LLM_MAX_THINKING_TOKENS`：默认模型是 thinking 模型，不限预算会把 `max_tokens` 全花在推理上。实测单次结构化调用 20–115s（不设）vs 7–12s（512）vs 1–4s（0）。一次问答约 10 次调用，不设就会表现为"界面一直转圈"。
- `EMBED_MODEL`：`nemotron-3.5-embed-1b` 对批量请求约 1/3 概率返回 `500 service inference failed`，而摄入按 chunk 整体重试 → 一个坏批就丢整块。换 `nvidia/nemotron-3-embed-1b`（同为 2048 维）即可。

### 3.4 加载示例库并验证（已加载过可跳过）

```bash
docker compose up -d --wait postgres
git clone https://github.com/NVIDIA/auto-ontology-eval.git ../auto-ontology-eval
(cd ../auto-ontology-eval && uv sync && cp .env.example .env && \
  POSTGRES_PASSWORD='<同 .env>' uv run python scripts/seed/seed_wwi.py \
  --database-name wideworldimporters --drop)
docker compose up -d --build
```

打开 <http://localhost:3000>，用管理员账号登录 → **Settings → Semantic Compilation** 开启编译 →
等提示 *Semantic compilation is ready* → 去 **Chat** 提问：

> What was revenue for the USB food flash drive - sushi roll in Pennsylvania in June 2015?

理想结果：答案 + 生成的 SQL + 走过的步骤（解析了哪些词条、怎么 join、怎么校验）。

## 4. 当前这份本地部署的现状（2026-11）

便于对照排查，实际以 `.env` 为准：

| 项 | 值 |
|---|---|
| 访问地址 / 管理员 | `http://localhost:3000` / `admin@nvidia.com` |
| 源库 | 示例库 `wideworldimporters`，`SOURCE_CONNECTION_STRINGS=...@postgres:5432` |
| 对话模型 | `nvidia/nemotron-3.5-lightning-30b-a3b`（四角色同款） |
| 嵌入模型 | `nvidia/nemotron-3-embed-1b`（默认 3.5 版批量会 500，已换） |
| 思考预算 | `LLM_MAX_THINKING_TOKENS=512`（不设会出现"无响应"观感） |
| 服务状态 | `auto-ontology` / `ingestion-service` / `frontend` 均 healthy；`/api/health` 三绿 |

简单问题约 2 分钟（20 个左右 step 事件），复杂或多轮可到 5 分钟（60+ 个 step），属正常；首字节通常 0.1s 内返回。

| Analysis | `/analysis` | 自定义分析（保存的 SQL 分析，带名称/标签；会做 SQL 校验并嵌入，问答命中时会出现在结果的 `custom_analyses_used` 里） |
| Analytics | `/analytics` | 分析记录与结果视图，可下载 |

| Semantic Compilation | **Enable Semantic Compilation** 开关、**Distinct Value Scanning**、编译状态（Running / Ready / Failed）、**Reset Semantic Layer**（**破坏性重建**） |

| Import / Export | 本体 YAML 导入导出（原生格式或 Apache Ossie） |

| Rules | 规则 = 一条保存下来的全局检索 + 要打给命中对象的标签；每次摄入自动重放，给新列补标签，删规则即回收这些标签 |
| PII Settings | **PII Detection** 开关：开启后摄入阶段会给含个人信息的列打 `PII` 标签，并传递到由这些列构建的属性上（opt-in，默认关） |
| Users | 成员、角色（admin / viewer）、邀请 |
| Single Sign-On | SSO 配置 |
| Agent Settings | **Visualize SQL Results** 开关（是否给查询结果出图表） |

## 6. 核心概念

| 概念 | 是什么 | 谁来动 |
|---|---|---|
| **Term（词条）** | 业务概念，如 *Customer*、*Invoice Line*，带描述、同义词、映射到的列 | 摄入自动生成初稿，人认证 |
| **SQL attribute** | 挂在词条下的受控 SQL 表达式（毛利、滚动合计…）。Agent 复用它，保证同一指标算法唯一 | 人写/认证，或从查询历史建议 |
| **Relationship** | 表之间怎么 join，含桥表（多对多）。由主外键推断 + 数据分布验证 | 自动，可人工修正 |
| **Semantic compilation** | 把上述定义编译成可检索的语义层。编译没完成 = 什么都答不出 | Settings 里开关，每次改定义后要复查状态 |
| **Certified** | 认证标记。认证过的名称/描述/SQL 属性优先进入候选 | 人 |

**关键区别**：摄入 ≠ 编译。摄入把表和列抽进目录；编译才生成词条、关系、SQL 属性并做嵌入。Chat 答不出时先看编译状态，不要一直重试。

## 7. 日常操作路径

### 7.1 接数据源

两种来源，**一次只用一种**（两条链路顺序相反，混用会互相打脸）：

- **UI 连接**（Settings → Connections）：有 UI 连接时，问答优先用它们；摄入只在 `CONNECTION_STRINGS` 为空时才用它们。
- **`CONNECTION_STRINGS`**：设了就优先用于摄入；问答在无 UI 连接时回退到它。

UI 连接的 API 顺序（权限 `connection:manage`）：

1. `POST /api/connections/test` — 验凭证并返回可选 schema；422 带驱动原始报错。
2. `POST /api/connections` — 201 只代表存下来了，摄入是 best-effort。
3. 验证：`GET /api/datasources/dbs` 看到库和表、`GET /api/semantic-compilation/status` 看进度、MCP `check_readiness` 无阻塞项。

支持引擎：PostgreSQL、MySQL、Databricks、Snowflake、ClickHouse、Trino、Kyuubi、HeavyDB（可 UI 加）；DuckDB、SQLite（只能连接串）。

凭证存放：未配 Vault 时连接对象（含密码）**明文存 Postgres**；四个 `VAULT_*` 都设了才走 Vault。

### 7.2 改本体（安全姿势）

1. 先看现状：MCP `search_terms` / `get_term` / `get_term_columns` / `get_term_sql_attributes` / `describe_table`。
2. 说清要改什么（改名、加 SQL 属性、改关系），别静默重写词汇表。
3. 写 SQL 属性前先校验：`POST /api/sql-attributes/validate`。**解析失败是 422，不是 `valid:false`**。
4. 用最小改动写入（权限 `catalog:edit`；403 = 角色不够，不是路径错）。
5. 改完复查：`GET /api/semantic-compilation/status`。
6. 正向 + 反向验证：MCP `check_answerable` / `ask_question`；确认"能答的确实答对、答不了的明确说不能答"。

> `POST /api/semantic-compilation/reset` 是**异步的、破坏性重建**（202，权限 `semanticCompilation:manage`）。别当清理手段随手调。

### 7.3 批量导入导出

- `POST /api/model/export` — 导出目录 + 语义层 YAML，`format` 可 `auto_ontology` 或 `ossie`。
- `POST /api/model/import` — multipart YAML；`replace`（默认 true）、`embed`（默认 true）。

导入会覆盖现有数据：先确认、先在隔离环境试、导入后做精确回读比对（导出前先备份同一范围）。

### 7.4 提问与读结果

- 单轮：不带 `conversation_id`。
- 多轮：客户端生成 UUID 作 `conversation_id`，每条回合复用。后端最多取最近 5 轮（≤12000 字符）把"那 8 月呢？"改写成独立问题；只喂问题/答案/SQL，不喂思考、图表、原始行。
- **必须等 `[DONE]` 再发下一轮**，同一会话并发会 `409 Conversation in progress`。
- 图表只在带 `conversation_id` 且查询真的执行了之后才发。

## 8. 对接 Agent

### 8.1 MCP（推荐）

```bash
AUTO_ONTOLOGY_API_URL=http://localhost:3000 \
  uvx --from "git+https://github.com/NVIDIA/auto-ontology.git#subdirectory=mcp" auto-ontology-mcp
```

客户端配置（Cursor 等）：`{"mcpServers": {"auto-ontology": {"url": "http://localhost:3003/mcp"}}}`
（注意 `/mcp` 后缀）。重启客户端，按提示登录 Auto-Ontology —— 登录态由客户端自己管理，**不要把 token 配到 MCP server 上**。

工具（全部只读，权限等于登录人）：

| 工具 | 用途 |
|---|---|
| `check_readiness` | 这个部署现在能不能答任何问题（编译层 + 活连接，一次报全部阻塞项） |
| `check_answerable` | 这个问题语义层覆盖得了吗（便宜的预检） |
| `ask_question` | **主力**：答案 + SQL + 行（行上限 100，附 `row_count`/`truncated`） |
| `search_terms` / `get_term` / `get_term_columns` / `get_term_sql_attributes` / `get_sql_attribute` / `describe_table` | 查语义层 |

注意 `databases` 非空 ≠ 能执行 SQL：目录比连接活得久，`can_execute_sql` 才是判据。

### 8.2 REST（脚本/定时任务）

```bash
curl -N http://localhost:3000/api/chat/completions \
  -H "x-api-key: $AUTO_ONTOLOGY_API_TOKEN" -H "Content-Type: application/json" \
  -d '{"question": "How many orders shipped last week?"}'
```

SSE 事件：`step`（进度）、`sql`（通过校验的 SQL）、`result`（答案+SQL+行+思考链）、`charts`、`error`，最后 `data: [DONE]`。

### 8.3 认证方式优先级

`/api/...` 统一在 `frontend/auth/resolve-user.ts` 解析：① 浏览器 session cookie → ② API token（`x-api-key` 或 `Bearer`）→ ③ MCP 的 OAuth bearer → ④ 受信调用方转发的 SSO ID token。

API token 规则：**代其所有者行事**（viewer 的 token 只能干 viewer 的事）；吊销立即生效；**token 不能造 token**（防泄漏后自我续命）。

角色只有两个：`admin`（全部权限）、`viewer`（只读 + 能用 chat + 能管自己的 token）。

## 9. 部署与运维

### 9.1 Kubernetes（官方方式）

```bash
helm repo add nvidia https://helm.ngc.nvidia.com/nvidia && helm repo update
# 先写 values 文件（编辑器中写、chmod 600、别进 git，别放命令行参数）
#   defaultModelsApiKey / postgresPassword / adminEmail / adminPassword / connectionStrings
helm install auto-ontology nvidia/auto-ontology -f auto-ontology-secrets.yaml
kubectl port-forward svc/frontend 3000:3000
```

`adminEmail`/`adminPassword` 必填（没有自助注册）；用户从别的地址访问时必须把 `appUrl` 设成那个确切 origin。

### 9.2 常用运维命令

| 目的 | 命令 |
|---|---|
| 看容器状态 | `docker compose ps -a` |
| 健康检查 | `curl http://localhost:3001/api/health`（或前端 `/api/health`） |
| 编译状态 | `GET /api/semantic-compilation/status`；ingestion 侧 `curl localhost:3002/semantic/status` |
| 重跑迁移 | `docker compose up -d auto-ontology-migrate frontend-migrate` 并读日志 |
| 停机保数据 | `docker compose down` |
| 清空重来 | `docker compose down -v`（**删数据**，先确认） |

### 9.3 开发者工作流（改这个项目本身）

```bash
./dev_tools/setup_env.sh --dev    # 只起 infra（postgres/pgadmin/ingestion）
cd frontend && pnpm dev           # Next.js
uv run uvicorn auto_ontology.server.__main__:create_app --factory --reload --host 127.0.0.1 --port 3001
```

`--ds`：前端在 Docker、FastAPI 在宿主机（前端镜像里烘了 `PYTHON_API_URL=http://host.docker.internal:3001`，所以必须 `python -m auto_ontology.server` 绑 `0.0.0.0:3001`）。

提交前跑（等同 CI 门禁）：`uv run ruff check auto_ontology/`、`uv run pytest auto_ontology dev_tools -q`、
`uv run python -m dev_tools.generate_backend_openapi`（改了任何 `@router` 的 docstring 也要重生成）、
`cd frontend && npx prettier --check . && pnpm lint && pnpm build`。

## 10. 故障排查速查

| 现象 | 大概率原因 | 处理 |
|---|---|---|
| `connection to server at "::1" ... refused` | 容器里写了 `@localhost` | 容器用 `SOURCE_CONNECTION_STRINGS=...@postgres:5432/...` |
| 页面全报 Better Auth default secret | 缺 `AUTH_SECRET` | 补上并重启 |
| 提问一直转圈/十几分钟才出答案 | 思考型模型没有预算上限 | 设 `LLM_MAX_THINKING_TOKENS=512`（或 0） |
| 摄入 `0/N row(s) embedded` | 嵌入模型批量 500 | `EMBED_MODEL=nvidia/nemotron-3-embed-1b`（维度一致） |
| 答不出、SQL 空 | 语义层没编译 | 看 `/api/semantic-compilation/status`，`calculated:false` 说明词汇表是空的 |
| `SQL doesn't reference any table known to the catalog` | **正在重新编译**（`running:true`）或连接失效 | 等编译完再测；查连接是否还有效 |
| 重启后左侧导航消失 | 浏览器握着过期 session cookie | 清 `localhost:3000` 站点数据后重登 |
| 登录/MCP 登录失败 | 迁移没跑干净 | 看 `docker compose logs frontend-migrate`，**即使 exit 0 也要读日志** |
| MCP 报 `Protected resource ... does not match` | `127.0.0.1` 与 `localhost` 写法不一致 | 设 `AUTO_ONTOLOGY_MCP_PUBLIC_URL` 为客户端实际使用的地址 |
| MCP 客户端看不到工具 / 无法登录 | OAuth discovery 不存在 | `curl -o /dev/null -w '%{http_code}' $URL/.well-known/oauth-authorization-server` 要 200 |
| `Model ... is not known to support structured output` | 客户端库注册表不认识新 router 模型（误报） | 已在 `llm_invoke` 里自动注册（仅 hosted 端点），自建 NIM 保留该告警 |
| 端口 5432 被占 | 宿主机已有 Postgres | 改 `POSTGRES_PORT`（只映射宿主机侧，容器内仍是 5432） |

排查原则：**先 `check_readiness` / 编译状态，再怀疑模型**。绝大多数"答不出来"是语义层没准备好或连接丢了，而不是模型不行。
